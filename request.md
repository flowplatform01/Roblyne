# Evenum → FlowPay Integration Review

## 1. Purpose and scope

This document describes the financial behavior implemented in the current Evenum codebase. It is intended for review by the FlowPay engineering team so that FlowPay can assess the existing integration boundary against its established production services, policies, payment models, security requirements, and operational standards.

This is an implementation review, not a proposed payment architecture. The descriptions below use the terminology and behavior present in the current Evenum application. Where a capability is not implemented, it is identified as such rather than inferred.

## 2. Current implementation summary

Evenum has three product pillars that can create financial ledger records:

| Pillar | User-facing activity | Ledger transaction type |
|---|---|---|
| Events | Registration for a ticket type whose price is greater than zero | `ticket` |
| Elections | Submission of a ballot in an election configured with a payment amount | `vote` |
| Campaigns | Submission to a campaign configured with a fixed payment amount | `campaign_response` |

The current financial implementation is an internal platform ledger. A paid activity calls the shared `recordTransaction` function, which:

1. validates that the gross amount is positive;
2. obtains the commission rate for the relevant pillar, falling back to the global rate and then to a hard-coded 5% fallback;
3. calculates the commission and organization earnings;
4. inserts a row into `financial_transactions`;
5. sets the transaction status to `completed`;
6. sets the payment provider to `platform`;
7. sets the settlement status to `pending`.

There is no external payment-provider SDK, FlowPay adapter, payment-intent creation route, provider transaction identifier, provider callback, webhook, refund endpoint, or payment retry mechanism in the current implementation.

## 3. Money movement in the current Evenum flows

### 3.1 Event ticketing

#### Configuration

An organization administrator creates an event and then creates one or more ticket types. Each ticket type stores:

- `eventId`
- `name`
- `description`
- `price`
- `currency`
- optional `quantity`
- `sold`
- optional sale start and end timestamps

The ticket type price is a decimal database value with precision 10 and scale 2. The default currency is `XAF`. The event itself does not contain a payment amount; payment configuration is held by each ticket type.

#### Registration sequence

The public frontend route is:

```text
/events/:eventId/register
```

The frontend uses `useRegisterForEvent` and submits:

```text
POST /api/events/:eventId/register
```

The request body currently contains:

```json
{
  "ticketTypeId": 123,
  "attendeeName": "Attendee name",
  "attendeeEmail": "attendee@example.com",
  "quantity": 1
}
```

The backend validates the event, visibility, publication status, event time window, invite code where applicable, ticket-type ownership, ticket sale window, event capacity, and ticket-type quantity. It then opens a database transaction and:

1. locks the event row;
2. checks event capacity;
3. locks the selected ticket-type row;
4. checks the ticket-type sale window and remaining quantity;
5. inserts a `tickets` row with status `valid`;
6. increments `ticket_types.sold`;
7. if the ticket price is greater than zero, inserts a `financial_transactions` row through `recordTransaction`.

The backend always issues one ticket per registration request. Although the request schema includes `quantity`, the current registration handler does not use it to issue multiple tickets or multiply the amount.

The ticket and financial ledger insert occur in the same database transaction. If the transaction fails, the registration does not complete. A successful response returns the ticket record, including its internal ticket ID, event title, ticket type name, ticket code, attendee information, status, and issue timestamp.

#### Free and paid ticket behavior

- A zero-price ticket creates a ticket but does not create a financial ledger record.
- A paid ticket creates a ticket and an internal completed ledger record.
- There is no external payment step before ticket issuance.
- There is no payment status attached to the ticket.
- There is no payment or transaction ID stored on the ticket.
- There is no refund or cancellation processing route. The ticket status values are `valid`, `used`, and `cancelled`; changing a ticket status does not create or update a financial record.

The ticket code is generated by Evenum and is used for entry validation. It is not a payment reference.

### 3.2 Campaigns and collections

#### Configuration

A campaign belongs to an organization and stores:

- `orgId`
- `title`
- `type`
- `status`
- `visibility`
- optional `goalAmount`
- `currentAmount`
- `requiresPayment`
- optional fixed `paymentAmount`
- `currency`
- configurable submission fields
- optional start and end timestamps

The supported campaign type values represented in the schema are:

```text
registration | contribution | donation | application | membership | merchandise | custom
```

The current submission handler uses the same fixed-payment behavior for all campaign types. The type value does not select a different payment implementation.

#### Submission sequence

The public frontend route is:

```text
/campaigns/:campaignId/participate
```

The frontend uses `useSubmitCampaignResponse` and submits:

```text
POST /api/campaigns/:campaignId/submit
```

The request body currently contains:

```json
{
  "submitterName": "Contributor name",
  "submitterEmail": "contributor@example.com",
  "data": {
    "field_id": "submitted value"
  }
}
```

The backend validates campaign visibility, active status, and the campaign time window. It calculates the amount as follows:

```text
paymentAmount = campaign.requiresPayment
  ? campaign.paymentAmount
  : 0
```

It then opens a database transaction and:

1. inserts a `campaign_responses` row;
2. sets `amountPaid` to the fixed campaign payment amount when it is greater than zero;
3. sets the response status to `confirmed` for a paid response, or `pending` for a free response;
4. for a paid response, increments `campaigns.current_amount`;
5. for a paid response, inserts a `financial_transactions` row through `recordTransaction`.

#### Contribution and donation behavior

The schema recognizes `contribution` and `donation` campaign types, but there is no separate variable-contribution or donation amount entered by the user. The current implementation records the campaign's configured fixed `paymentAmount`, if paid submissions are enabled. There is no separate contribution entity, donation entity, donor wallet, payment reference, or collection payment status.

#### Collection status

Campaign response status is separate from financial transaction status:

```text
pending | confirmed | rejected
```

For a paid submission, the response is written as `confirmed` immediately and the financial ledger transaction is written as `completed` immediately. There is no external payment confirmation state between submission and confirmation.

### 3.3 Voting and elections

#### Configuration

An election stores:

- `orgId`
- `title`
- `status`
- `visibility`
- authentication and eligibility settings
- optional invite code
- optional start and end timestamps
- `requiresPayment`
- optional `paymentAmount`
- `currency`

The default election currency is `XAF`.

Positions and candidates are separate records. Candidates also contain `requiresPayment`, `paymentAmount`, and `currency` fields in the database schema. The current vote submission route does not use candidate-level payment fields; paid-voting calculations use the election-level payment settings.

#### Frontend payment gate

The public frontend route is:

```text
/elections/:electionId/vote
```

When the election requires payment, the frontend shows a payment screen. It supports the platform setting values:

```text
quantity_first | amount_first
```

The frontend calculates the displayed amount from the election-level `paymentAmount`, selected candidate count, and vote quantity. In `amount_first` mode it derives a vote quantity from the entered amount.

The current payment screen is simulated locally. The handler:

1. checks the client-side lifecycle state;
2. sets a processing indicator;
3. waits two seconds with `setTimeout`;
4. checks whether the election deadline has passed;
5. sets a local `hasPaid` flag;
6. calls the normal ballot submission function.

No external payment request is made by this screen. No payment token, transaction reference, or provider response is collected.

#### Ballot submission sequence

The frontend uses `useSubmitVote` and submits:

```text
POST /api/elections/:electionId/vote
```

The request body contains:

```json
{
  "selections": [
    {
      "positionId": 10,
      "candidateIds": [20]
    }
  ],
  "voteQuantity": 1,
  "inviteCode": "OPTIONAL",
  "voterEmail": "OPTIONAL"
}
```

The backend validates:

- election existence and visibility;
- at least one selected candidate;
- no duplicate position entries;
- that every position belongs to the election;
- that candidate IDs are unique within a position;
- each position's `maxSelections`;
- candidate membership in the selected position;
- election status and time window;
- invite code for invite-only elections;
- allowlisted voter email where eligibility mode is `allowlist`;
- one ballot per voter identifier.

The voter identifier is selected in this order:

```text
user:<authenticated user id>
email:<lowercased voter email>
session:<Express session id>
```

Inside one database transaction the backend:

1. inserts a `votes` row with the election ID, voter identifier, and vote quantity;
2. inserts the related `vote_selections` rows;
3. when the election requires payment and has a positive payment amount, calls `recordTransaction`.

The paid-vote gross amount is calculated as:

```text
election.paymentAmount
  × selected candidate count
  × vote quantity
```

The response to a successful request is only:

```json
{
  "message": "Vote recorded"
}
```

No transaction identifier or payment reference is returned to the voter. The current implementation does not independently verify payment on the server before accepting a paid ballot. The payment gate is a client-side simulation; a direct request to the vote endpoint follows the ballot validation and can create the vote and completed ledger record without a provider payment.

## 4. Existing payment and financial data model

### 4.1 `financial_transactions`

This table is the internal financial ledger for revenue-generating activity.

| Field | Current meaning |
|---|---|
| `id` | Evenum's serial internal transaction ID |
| `orgId` | Organization associated with the transaction |
| `pillar` | `event`, `election`, or `campaign` |
| `entityId` | ID of the event, election, or campaign |
| `entityTitle` | Snapshot of the associated entity title |
| `transactionType` | `ticket`, `vote`, or `campaign_response` |
| `grossAmount` | Gross amount, stored as decimal precision 12/scale 2 |
| `commissionRate` | Decimal fraction, for example `0.0500` for 5% |
| `commissionAmount` | Calculated commission, rounded to two decimal places |
| `orgEarnings` | Gross amount minus commission, rounded to two decimal places |
| `currency` | Currency code text, default `XAF` |
| `status` | Default and currently-created value `completed`; schema comment lists `completed`, `refunded`, and `disputed` |
| `paymentProvider` | Default and currently-created value `platform` |
| `settlementStatus` | Default and currently-created value `pending` |
| `settlementId` | Optional link to a settlement batch |
| `payerName` | Optional payer/participant name |
| `payerEmail` | Optional payer/participant email |
| `createdAt` | Ledger creation timestamp |

The ledger does not currently contain a provider transaction ID, payment intent ID, authorization code, receipt number, idempotency key, failure reason, callback timestamp, refund amount, dispute reference, or provider metadata JSON field.

`entityId` and `pillar` together identify the Evenum business object. For events, elections, and campaigns, the organization is also available through the `orgId` foreign-key relationship. The ticket ID, campaign response ID, and vote ID are not stored in the financial transaction row.

### 4.2 `settlements`

Settlements group completed ledger transactions for organization payout processing.

| Field | Current meaning |
|---|---|
| `id` | Evenum settlement batch ID |
| `orgId` | Organization receiving the settlement |
| `amount` | Sum of organization earnings in the batch |
| `currency` | Currency of the batch |
| `status` | `pending_settlement`, `ready`, `released`, or `completed` |
| `transactionCount` | Number of ledger transactions included |
| `payoutMethod` | `bank_transfer` or `mobile_money` when requested by an organization |
| `payoutAccount` | Organization-provided payout account text |
| `notes` | Optional settlement notes |
| `releasedAt` | Timestamp set when status becomes `released` |
| `completedAt` | Timestamp set when status becomes `completed` |
| `createdAt` | Settlement creation timestamp |

When an organization requests a payout, Evenum locks completed ledger rows with `settlementStatus = pending`, requires all rows in the batch to use one currency, creates a settlement, and updates those ledger rows to `settlementStatus = ready`.

Platform administrators can advance the settlement in this order only:

```text
pending_settlement → ready → released → completed
```

When the settlement becomes `completed`, the associated ledger rows are updated to `settlementStatus = completed`. This workflow records and advances Evenum's internal settlement state; it does not call an external payout service.

### 4.3 Related business records

The related tables store business outcomes rather than provider payment records:

- `tickets`: `eventId`, `ticketTypeId`, attendee name/email, Evenum-generated `ticketCode`, `status`, check-in timestamp, issue timestamp.
- `campaign_responses`: `campaignId`, submitter name/email, JSON submission data, `amountPaid`, response `status`, submission timestamp.
- `votes`: `electionId`, `voterIdentifier`, `quantity`, vote timestamp.
- `vote_selections`: links a vote to a position and candidate.

None of these records has a foreign-key reference to `financial_transactions` or a payment-provider transaction record.

## 5. Transaction and payment states

Evenum currently has several distinct state systems:

### Financial transaction status

Financial transactions created by the current code use:

```text
completed
```

The schema comment identifies `refunded` and `disputed` as possible values, but the current API contains no route that creates, updates, or processes those states. There are no implemented `initiated`, `pending`, `successful`, `failed`, `cancelled`, or `expired` payment states in the financial ledger.

### Settlement status

Ledger settlement status uses:

```text
pending → ready → completed
```

The related settlement record exposes the more detailed sequence:

```text
pending_settlement → ready → released → completed
```

These are payout/settlement states, not payment authorization states.

### Product record states

- Event: `draft`, `published`, `cancelled`, `completed`; ticket: `valid`, `used`, `cancelled`.
- Campaign: `draft`, `active`, `ended`; response: `pending`, `confirmed`, `rejected`.
- Election: `draft`, `active`, `ended`; vote records have no status field.

The current implementation does not derive a payment state from these product states and does not automatically reverse ledger records when a product record is cancelled.

## 6. Organization and recipient context

An organization is represented by the `organizations` table:

- `id`
- `name`
- unique `slug`
- description and branding fields
- `ownerId`
- creation timestamp

Events, elections, and campaigns each have a required `orgId` foreign key to `organizations`. The organization owner is represented by `organizations.ownerId`. Additional organization members are stored in `organization_members` with `admin` or `member` roles.

The current organization model does not contain a separate recipient, beneficiary, merchant, FlowPay account, payout destination ID, legal entity ID, or verified settlement profile. The available destination context for a financial ledger transaction is:

- Evenum `orgId`;
- organization name and slug;
- organization owner ID;
- the activity pillar and entity ID;
- payout method and payout account, when an organization has requested an internal settlement.

The event, election, or campaign is owned by the organization through `orgId`. The payer context, where collected, is the participant name and email copied into the ledger row.

## 7. API surface at the current integration boundary

### Collection and business-record endpoints

```text
POST /api/events/:eventId/register
POST /api/campaigns/:campaignId/submit
POST /api/elections/:electionId/vote
```

These endpoints currently perform both the business-record operation and, where applicable, internal ledger creation. There is no separate payment initiation or payment confirmation endpoint.

### Configuration endpoints relevant to payment presentation

```text
GET   /api/admin/platform-settings/public
GET   /api/admin/platform-settings
PATCH /api/admin/platform-settings
```

The public endpoint exposes payment presentation settings including `paymentMode`, `defaultCurrency`, and `supportedCurrencies`. The authenticated admin endpoint can update the payment mode and support contact fields. The current admin update route does not configure provider credentials or provider connection details.

### Organization finance endpoints

```text
GET  /api/organizations/:orgId/finance
GET  /api/organizations/:orgId/finance/transactions
GET  /api/organizations/:orgId/finance/settlements
GET  /api/organizations/:orgId/finance/export
POST /api/organizations/:orgId/finance/settlements
GET  /api/organizations/:orgId/analytics
```

These routes expose internal summaries, transaction history, settlements, CSV exports, and organization analytics. Organization finance access is restricted to authenticated organization owners and administrators.

### Platform finance endpoints

```text
GET   /api/admin/finance/stats
GET   /api/admin/finance/transactions
GET   /api/admin/finance/settlements
POST  /api/admin/finance/settlements
PATCH /api/admin/finance/settlements/:id
GET   /api/admin/finance/org-balances
GET   /api/admin/finance/commission-config
PATCH /api/admin/finance/commission-config/:pillar
GET   /api/admin/finance/export
```

These routes are restricted to platform administrators and operate on Evenum's internal ledger and settlement records.

## 8. Integration boundary: current ownership

### Evenum currently owns

Evenum currently owns:

- event, ticket type, campaign, election, organization, attendee, submitter, and voter records;
- lifecycle and eligibility validation;
- ticket issuance and Evenum ticket codes;
- ballot validation and vote recording;
- campaign response recording and `current_amount` aggregation;
- calculation of the paid amount for each supported paid flow;
- commission calculation and internal financial ledger creation;
- internal organization balances and settlement state;
- participant-facing success and error messages;
- authenticated organization and platform-admin access to financial records.

### Not currently implemented in Evenum

The current codebase does not implement:

- external payment-provider selection or configuration;
- payment-session or payment-intent creation;
- a provider checkout redirect or embedded provider widget;
- provider-side customer or payer identity mapping;
- provider transaction/reference persistence;
- asynchronous payment confirmation;
- payment callbacks or webhooks;
- signature verification for payment notifications;
- provider-specific success, failure, cancellation, expiration, refund, or dispute processing;
- idempotency keys or replay handling for payment requests;
- reconciliation against an external payment report;
- external payout execution.

The current boundary therefore exposes an Evenum business action that synchronously records a completed internal financial transaction. It does not currently expose a provider-neutral payment object or a callback contract.

## 9. Current assumptions and dependencies

The following assumptions are present in the implementation:

1. **Synchronous completion:** A paid ticket registration, paid campaign response, or paid vote writes the business record and ledger record during the same request.
2. **Immediate completion state:** The internal ledger is created with `status = completed`; no provider confirmation is awaited.
3. **Internal provider label:** New records use `paymentProvider = platform`, described in code as simulated platform processing.
4. **Positive gross amount:** `recordTransaction` rejects zero or negative amounts.
5. **Decimal amounts:** Database monetary fields use decimal values with two fractional digits. Commission calculations are rounded to two decimal places in application code.
6. **Currency text values:** Currency is stored as text. The default platform and most product currency defaults are `XAF`; the candidate schema has a `USD` default, although candidate-level payment is not used by the vote route.
7. **One currency per settlement batch:** A withdrawal request fails if the pending ledger rows contain more than one currency.
8. **Fixed campaign amount:** Paid campaign participation uses the campaign's configured fixed amount; the participant does not submit a contribution amount.
9. **Election amount multiplication:** Paid voting multiplies the election amount by selected candidate count and vote quantity.
10. **Client-side voting payment gate:** The paid-voting UI simulates a two-second confirmation before submitting the ballot. The server vote endpoint does not receive or validate a payment reference.
11. **No payment idempotency:** No payment idempotency key is accepted or persisted. Vote uniqueness is enforced separately through `electionId` plus `voterIdentifier`.
12. **No provider retry path:** Client mutations may display an error, but there is no provider retry, payment reconciliation, or status polling flow.
13. **Business-record rollback with internal ledger:** In the event, campaign, and election paid flows, business-record and ledger writes are in the same database transaction. This is an internal database atomicity property, not an external payment atomicity guarantee.
14. **Participant identification:** Paid event and campaign ledger rows store name and email. Paid election ledger rows currently pass voter email only when it is provided by the request.
15. **Local authenticated sessions:** Evenum uses an HTTP-only Express session backed by PostgreSQL for authenticated users and organization administration. Public collection endpoints can be used without an authenticated account, subject to each product's visibility and eligibility rules.

## 10. Evenum-side integration gaps identified by inspection

The current implementation does not expose several pieces of information or behavior that a production payment integration may require FlowPay to evaluate:

- There is no persistent provider transaction/reference field.
- A ticket, campaign response, or vote cannot be directly linked to a financial ledger row through a business-record foreign key.
- There is no payment-attempt record separate from the completed internal ledger entry.
- There is no callback or webhook endpoint.
- There is no server-side paid-vote proof or provider payment reference in the vote request.
- There is no payment failure, cancellation, expiration, refund, or dispute handler.
- There is no idempotency or replay contract for provider notifications.
- There is no provider-specific authentication configuration in the current admin settings.
- There is no recipient/destination identifier other than the Evenum organization context and the free-form payout account stored on a settlement request.
- The current registration request includes `quantity`, but the event handler currently issues one ticket and records the selected ticket price once.
- Campaign types include donation and contribution labels, but the current flow records only a configured fixed campaign amount.
- A successful collection response does not return an Evenum transaction ID to the participant.
- Existing receipt-like outputs are the event ticket code and submission/vote success responses; no payment receipt or provider reference is generated.

These are observations about the current Evenum side. They are not instructions for FlowPay architecture or policy.

## 11. Requested FlowPay engineering review

Evenum is presenting its current production behavior and integration boundary for technical review. We would appreciate the FlowPay engineering team's guidance on how the existing implementation should be evaluated against the established FlowPay production environment, including:

- applicable integration specifications and supported payment flows;
- required identifiers for Evenum organizations, activities, participants, transactions, and destinations;
- required request and response payloads;
- authentication and authorization requirements;
- webhook or callback requirements;
- transaction status mapping;
- recipient or destination requirements;
- reconciliation and reporting requirements;
- supported currencies, amount precision, minimums, maximums, and rounding rules;
- security, signature, replay-protection, and data-handling requirements;
- operational requirements such as timeouts, retries, monitoring, and support procedures;
- any additional conditions Evenum needs to satisfy before production integration.

Please review whether the current Evenum data, synchronous collection flows, internal ledger states, organization context, and identified gaps align with the existing FlowPay production requirements, and advise on the integration information or adjustments required from the Evenum side.
