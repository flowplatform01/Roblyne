EVENUM — DEEP PRODUCTION AUDIT, PERFORMANCE HARDENING & LOGICAL/UX GAP REMEDIATION

IMPORTANT: This is a serious production audit and remediation pass.

I have personally gone through the application as a real human user and identified multiple concrete gaps. I do NOT want another generic UX-polish pass, generic checklist, or superficial “everything looks good” implementation.

EVENUM is already a mature application with substantial functionality. Do not rebuild it, do not downgrade it to an MVP, and do not introduce unnecessary architectural changes.

The objective is:

1. Investigate the concrete issues below.
2. Fix the verified issues properly.
3. Audit the rest of the application for other issues belonging to the same categories.
4. Preserve existing functionality and architecture wherever it is already sound.
5. Avoid regressions.
6. Use engineering judgment instead of blindly implementing every sentence literally.
7. Test the actual application after changes.

This should feel like a senior engineering + product + UX production-readiness audit.

==================================================
0. FIRST RULE: INVESTIGATE BEFORE CHANGING
==================================================

Before modifying anything, inspect the existing implementation and understand how it currently works.

For every issue:

- reproduce it
- identify the actual root cause
- determine whether it is frontend, backend, data, API, state, caching, configuration, payment integration, or UX logic
- determine the correct fix
- implement the smallest robust solution that solves the underlying problem

Do NOT simply hide symptoms.

Do NOT add another loader to hide a slow request.

Do NOT create duplicate systems if one already exists.

Do NOT redesign unrelated areas.

Do NOT remove working functionality.

Do NOT make assumptions about business rules where the existing implementation already establishes a rule.

Where the correct behavior is ambiguous, inspect related flows and existing architecture and choose the safest mature behavior.

==================================================
1. CRITICAL PERFORMANCE ISSUE — EVENUM FEELS EXTREMELY SLOW
==================================================

This is currently one of the biggest concerns.

The application feels noticeably slow in real human use.

This is NOT just a missing loading state.

Even with skeleton loading already implemented, the application can feel slow when:

- opening the application
- navigating between areas
- opening pages
- opening modals
- performing interactions
- loading data
- returning to previously visited areas

In particular, if a simple modal takes a noticeable amount of time to become usable, investigate why.

Do not assume the solution is “more skeletons.”

Perform a serious performance investigation.

Inspect:

- initial application boot
- JavaScript bundle loading
- code splitting
- lazy loading
- route loading
- component mounting
- unnecessary component remounts
- expensive React renders
- unnecessary rerenders
- state subscriptions
- context updates
- data fetching
- duplicate requests
- sequential requests that could safely run in parallel
- unnecessary authentication/session calls
- unnecessary organization/workspace calls
- API latency
- database/API bottlenecks visible from the application
- cache behavior
- stale-while-revalidate opportunities
- local persistence
- service worker/PWA behavior
- image loading
- font loading
- modal rendering
- dialogs/sheets that unnecessarily wait for unrelated data
- large components loaded before they are needed
- blocking initialization
- expensive calculations during interaction
- unnecessary effects
- request waterfalls
- repeated data fetching after navigation
- unnecessary full-page refresh behavior

IMPORTANT:

A modal that only needs local UI state should NOT wait for a network request unless there is a legitimate reason.

Likewise, navigating to a page should not unnecessarily block the entire interface while unrelated data loads.

Where safe, make the application feel immediate:

USER ACTION
→ IMMEDIATE UI RESPONSE
→ LOCAL/CACHED CONTENT WHERE AVAILABLE
→ DATA RESOLUTION IN BACKGROUND
→ FINAL STATE

rather than:

USER ACTION
→ WAIT
→ WAIT
→ SPINNER/SKELETON
→ EVENTUAL UI

Use caching, prefetching, parallelization, memoization, code splitting, progressive rendering, and other techniques ONLY where justified by the actual architecture.

Do not introduce unnecessary complexity.

==================================================
2. PERFORMANCE TARGET: NATIVE-APP-LIKE FEEL
==================================================

Use mature applications such as WhatsApp as a mental reference for perceived responsiveness.

When a user opens an already-used application or revisits an already-known area, it should feel extremely fast.

Where valid cached state exists:

- show it immediately
- refresh it intelligently
- avoid replacing usable content with a blank/loading state

Where a screen is genuinely cold:

- render the application shell immediately
- render structural skeletons where appropriate
- progressively resolve content
- avoid blocking unrelated UI

The goal is NOT to fake speed.

The goal is to make EVENUM genuinely fast and architecturally responsive.

Measure before and after where practical.

Identify the largest sources of latency rather than merely optimizing random components.

==================================================
3. SKELETON LOADING — KEEP IT, BUT DO NOT USE IT AS A BANDAGE
==================================================

Skeleton loading has already been introduced.

Keep and refine it where appropriate.

However, do not use skeleton loading to disguise underlying performance problems.

For every major loading state, distinguish:

- application initialization
- route loading
- data loading
- component loading
- mutation/action processing
- background refresh

Use the appropriate behavior for each.

If something is genuinely slow because of a backend/API bottleneck, identify and report the bottleneck instead of simply adding a prettier loader.

4. CURRENCY AUDIT — REMOVE INCORRECT USD/DOLLAR REPRESENTATION
==================================================

This is a concrete production issue.

EVENUM's relevant financial/cost UI is intended to use **Franc CFA / XAF**, not USD.

I have found multiple places where the UI still displays dollar/USD assumptions.

This is a red flag.

Perform a FULL currency audit across the entire application.

Inspect:

- events
- ticket creation
- ticket pricing
- ticket purchase flows
- event public pages
- campaigns
- campaign contribution/payment flows
- elections/voting fees where applicable
- checkout
- payment screens
- financial dashboards
- balances
- transaction history
- withdrawal interfaces
- fees
- receipts
- summaries
- confirmation screens
- public pages
- forms
- validation messages
- empty states
- success/error messages
- notifications
- generated/preview content
- admin interfaces
- organization interfaces
- mobile and desktop variants

Do not merely replace "$" visually.

Determine where currency is coming from.

Audit:

- formatting functions
- currency configuration
- default values
- database values
- API responses
- frontend assumptions
- placeholders
- examples
- validation
- internationalization/localization
- public rendering

EVENUM should consistently represent the intended currency as **XAF / FCFA** wherever financial amounts are being represented.

Use one consistent formatting convention throughout the application.

Do not create a situation where some screens say USD, others XAF, and others FCFA inconsistently.

IMPORTANT:

Do not blindly change legitimate third-party/payment-provider currency behavior if the provider requires a specific representation internally.

Separate internal/provider requirements from what the EVENUM user sees.

The user-facing experience must be correct.

Search the codebase for hardcoded "$", "USD", dollar assumptions, sample financial values, and default currency configuration.

Also inspect areas I did not explicitly mention.

5. EDITABILITY / UPDATEABILITY GAP
==================================================

This is a major product maturity issue.

Humans make mistakes.

The current application appears to have multiple objects that, once created, cannot be edited properly.

This is not acceptable for a mature production platform unless there is a deliberate business/security reason.

Audit editability across the ENTIRE PLATFORM.

At minimum inspect:

EVENTS
- event name
- description
- branding
- imagery
- dates/times where logically allowed
- location
- ticket configuration where safely editable
- public information
- settings

CAMPAIGNS
- campaign name
- description
- branding
- imagery
- goals
- public information
- configuration where safely editable

ELECTIONS / VOTING
- election title
- description
- branding
- candidate information
- candidate names
- candidate descriptions
- candidate imagery
- positions
- non-critical configuration
- other metadata

ORGANIZATIONS
- profile information
- branding
- descriptions
- images
- contact/public information where applicable

TICKETS / COLLECTIONS
- editable metadata/configuration where safe
- pricing/configuration where business rules permit

OTHER USER/ORGANIZATION-CREATED CONTENT
- inspect the whole platform rather than limiting this to the examples above.

For every entity, determine:

A. Should it be editable?
B. If yes, what fields should be editable?
C. Under what lifecycle/status conditions?
D. What should happen if editing affects already-published/public information?
E. Does the system need an audit/history trail?
F. Are there fields that must become immutable after a certain point for integrity?

DO NOT make everything blindly editable.

For example, a vote, completed transaction, payment record, or immutable financial record must not simply become editable.

The correct principle is:

USER-CREATED CONFIGURATION
→ EDITABLE WHERE SAFE

SERVER-AUTHORITATIVE / FINANCIAL / HISTORICAL RECORD
→ PROTECTED

LIVE/PUBLISHED CONTENT
→ EDITABLE WITH APPROPRIATE RULES

If editing a live election/campaign/event could materially affect participants, determine whether the change should:

- be allowed
- require confirmation
- be restricted
- create an audit record
- require a new version
- require a status transition

Use mature platform logic.

15. PAYMENT SANDBOX / DEVELOPMENT ENVIRONMENT
==================================================

This is another important issue.

Currently, payment-dependent flows are failing during testing.

Examples may include:

- event ticket purchase
- campaign contribution/payment
- paid voting
- other payment-required flows

EVENUM needs a proper distinction between:

DEVELOPMENT / TEST
and
PRODUCTION

During development/testing, there should be a legitimate sandbox/simulation mechanism so the entire product can be tested end-to-end without requiring real money or relying on production payment credentials.

IMPORTANT:

Do NOT create a fake payment system that bypasses the actual payment architecture.

Instead inspect the existing payment abstraction/integration and determine whether it already supports:

- provider sandbox
- test credentials
- mock provider
- simulated transaction adapter
- development payment mode
- deterministic test outcomes

If there is an existing abstraction, use it.

If not, introduce the smallest clean abstraction necessary.

The desired behavior is conceptually:

DEVELOPMENT / TEST
→ safe sandbox/simulation
→ realistic payment lifecycle
→ success/failure/pending scenarios
→ webhook/state transitions can be tested
→ no real money

PRODUCTION
→ actual configured payment provider
→ real payment flow

The application should not randomly fail simply because real production payment credentials are not present in development.

Also test:

- successful payment
- failed payment
- cancelled payment
- pending payment
- duplicate callback/webhook
- retry
- timeout
- user closes payment flow
- payment succeeds but client disconnects
- payment status reconciliation

Financial state must remain server-authoritative.

Do NOT expose a development bypass in production.

Do NOT allow client-side manipulation of payment success.

If the application already has a sandbox mechanism, investigate why it is not being used or why flows are currently failing.
