# EVENUM — Continuous World-Class Production Engineering, Adversarial QA & Autonomous Hardening Loop

## Mission

Evenum is no longer a prototype, MVP, demonstration, or experimental application.

It is intended to operate as a serious, production-grade participation platform.

Treat this codebase with the engineering discipline that would be expected for a high-importance product operated at significant scale.

The objective of this phase is not to add random features.

The objective is to continuously discover and eliminate:

* hidden bugs
* edge-case failures
* lifecycle inconsistencies
* race conditions
* state-management problems
* data integrity issues
* security weaknesses
* performance bottlenecks
* accessibility problems
* responsive/mobile issues
* browser-specific failures
* PWA issues
* navigation inconsistencies
* incomplete states
* broken recovery paths
* observability gaps
* architectural weaknesses
* poor UX decisions
* inconsistent business rules
* dead or unreachable functionality
* incorrect assumptions
* regressions
* technical debt that can become a production failure

The standard is not:

> "The application works when I click through the happy path."

The standard is:

> "The application has been investigated deeply enough that a serious production team can trust it under normal usage, abnormal usage, concurrent usage, failure conditions, unusual data, lifecycle transitions and real-world environments."

---

# 1. ENTER A CONTINUOUS ENGINEERING LOOP

Operate in a continuous loop:

**Inspect → Hypothesize → Reproduce → Diagnose → Fix → Test → Stress → Re-test → Review → Continue**

Do not stop after finding the first issue.

Do not assume the absence of visible errors means the system is healthy.

After every meaningful change:

1. Re-run the affected tests.
2. Re-test adjacent functionality.
3. Test the relevant edge cases.
4. Check for regressions.
5. Re-evaluate the underlying architecture.
6. Continue investigating the next potential weakness.

Continue until the remaining findings are either:

* intentionally accepted product decisions,
* genuinely irrelevant,
* impossible within the supported architecture,
* or explicitly documented as requiring external infrastructure.

Do not manufacture work simply to appear busy.

Every change must have a reason.

* payment confirmation
* candidate selection
* result calculation
* counters
* participant counts

* duplicate votes
* duplicate transactions
* stale reads

# 8. ORGANISATION & TENANT ISOLATION

Perform an adversarial multi-organisation test.

* see another organisation's private data
* modify another organisation's resources
* access another organisation's transactions
* access another organisation's candidates
* access another organisation's configuration
* access another organisation's reports
* affect another organisation's lifecycle
* access another organisation's administrative resources

* API calls

# 9. AUTHORIZATION AUDIT

Do not only test whether pages are hidden.

Verify authorization at the actual backend boundary.

For every sensitive action, ask:

> "What happens if a user manually calls this endpoint without having permission?"

Test:

* organisation admins
* operators
* ordinary users
* public users
* unauthenticated users
* users belonging to another organisation

Ensure UI restrictions and backend authorization agree.

---

# 10. LIFECYCLE CONSISTENCY

Audit the complete lifecycle of every major resource.

Do not assume lifecycle correctness because the countdown looks correct.

For every time-sensitive resource, verify:

**Draft → Scheduled → Active → Closing → Ended → Completed/Archived**

where those states are applicable.

Verify that every dependent system respects the lifecycle.

For example, when voting ends:

* voting must stop
* payment for participation must behave correctly
* UI must reflect ended state
* APIs must reject invalid actions
* cached pages must not incorrectly permit participation
* background jobs must respect the state
* Socket.IO updates must remain consistent
* results must remain accessible according to configuration
* shared pages must show the correct state

Investigate all similar lifecycle dependencies throughout Evenum.

# 25. CHANGE MANAGEMENT

Before every meaningful modification:

1. Understand the existing behaviour.
2. Identify the root cause.
3. Determine affected dependencies.
4. Make the smallest appropriate change.
5. Test the change.
6. Test adjacent functionality.
7. Check for regressions.

Prefer controlled improvements over broad rewrites.

---

# 26. PRODUCTION READINESS GATE

Do not declare the application healthy merely because the build succeeds.

The final assessment should consider:

### Functional integrity

Does the product actually perform its intended business operations correctly?

### Reliability

Does it remain stable under abnormal conditions?

### Performance

Does it remain responsive under realistic workloads?

### Scalability

Can critical workflows handle increasing concurrent activity?

### Security

Are sensitive operations properly protected?

### Data integrity

Can critical records become duplicated, lost or inconsistent?

### Lifecycle correctness

Do resources behave correctly throughout their complete lifecycle?

### UX

Does the application remain clear and polished under edge cases?

### Accessibility

Can different users operate the product effectively?

### Internationalisation

Are supported languages genuinely complete?

### Portability

Can the application operate independently of the development platform?

### Observability

Can production failures actually be diagnosed?

# 27. CONTINUOUS LOOP RULE

After completing one complete audit, do not immediately stop.

Start another pass from a different perspective.

For example:

**Pass 1 — Functional correctness**

Look for broken workflows.

**Pass 2 — Adversarial testing**

Try to break workflows intentionally.

**Pass 3 — Concurrency**

Try simultaneous operations.

**Pass 4 — Failure recovery**

Remove services, interrupt networks, reload pages and retry operations.

**Pass 5 — Mobile**

Test real mobile interaction patterns.

**Pass 6 — Security**

Attempt unauthorized access and manipulation.

**Pass 7 — Performance**

Investigate expensive operations and large datasets.

**Pass 8 — UX**

Look for friction, ambiguity and inconsistent feedback.

**Pass 9 — Data integrity**

Verify persistence, transactions and lifecycle transitions.

**Pass 10 — Regression**

Re-test previously completed critical functionality.

Then repeat intelligently where meaningful.

* the application will be publicly launched at scale
* thousands or millions of users may eventually interact with it
* a major election may suddenly generate enormous concurrent traffic
* organisations will depend on its records
* financial information must be trustworthy
* users will access it from unreliable networks
* users will use old and new devices
* users will behave unpredictably
* production incidents will have real consequences

Do not optimise for "looks good in development."

Optimise for:

**correctness, resilience, observability, scalability, security, accessibility, performance and exceptional user experience.**

* rebuild Evenum

* imitate another platform
* add features simply because they are technically possible

* create unnecessary abstractions
* introduce unnecessary dependencies
* make speculative changes

# FINAL STANDARD

The desired outcome is not:

> "I couldn't find any more bugs."

The desired outcome is:

> "I systematically investigated the application from multiple engineering perspectives, actively attempted to break it, verified the critical business flows, tested edge cases and failure conditions, validated the architecture, hardened genuine weaknesses, and confirmed that existing functionality continues to work correctly."

Evenum should emerge from this process feeling like a mature product that has been subjected to serious engineering scrutiny—not like an application that merely passed a happy-path demonstration.

Be autonomous.

Be skeptical.

Be methodical.

Be conservative with changes.

Be aggressive with testing.

Find problems before users do.

Fix root causes.

Verify every fix.

Continue the loop intelligently.

**Production quality is the goal. Passing a checklist is not.**
