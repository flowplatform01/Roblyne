Good work so far. We are now at another refinement and production-readiness stage.

Do not rebuild existing functionality or introduce unnecessary changes. Inspect the current implementation first, understand the existing design system and payment integration, then make only the changes that are genuinely necessary.

1. Theme Selector Placement

The current theme selector is exposed in the main header.

Review this placement and move the theme preference into the same user-preference area used for language selection.

The intended experience is:

* The application detects the user’s system language by default.
* Language remains accessible from the existing side menu / preference area.
* Theme preference should also live in that same preference area.
* Remove the standalone theme control from the main header if it is currently there.
* Keep the interface clean and avoid adding unnecessary header controls.

Theme options should remain:

* System
* Light
* Dark

The default preference should be System.

The system preference should follow the device/browser preference until the user explicitly chooses another option.

Once manually selected, persist that preference across sessions.

Do not break the existing language preference or navigation.

5. Sandbox → Production Transition Readiness

The current FlowPay environment is understood to be operating in sandbox mode.

Sandbox transactions should therefore be treated as simulations of the production payment flow, not as evidence that real funds are currently moving.

Inspect Evenum’s implementation and determine whether it is structurally ready for the same integration to operate against the production environment once FlowPay authorizes the switch.

Specifically verify:

* environment configuration is cleanly separated;
* sandbox credentials are not hardcoded;
* production credentials can be supplied securely;
* production endpoints can be configured without code rewrites;
* transaction references remain reliable;
* webhook/callback handling does not depend on sandbox-only behaviour;
* payment status handling works for asynchronous production behaviour;
* failures are handled safely;
* no test-only assumptions leak into production;
* no mock payment path is accidentally used in production;
* sensitive credentials are never exposed to the client;
* logging does not expose sensitive payment information.

If anything on the Evenum side would prevent a seamless transition, identify and fix it.

⸻

6. Do Not Pretend to Verify What Is Not Accessible

If the actual FlowPay production environment, credentials, operational dashboard, production endpoints, or live transaction capability are not accessible from this development environment, do not claim that FlowPay itself has been verified as production-ready.

Instead:

1. Verify everything that can genuinely be verified from Evenum.
2. Identify anything that requires FlowPay-side confirmation.
3. Clearly separate:
    * Verified on Evenum
    * Requires FlowPay confirmation
    * Blocked by unavailable production access

The goal is accurate engineering readiness, not a false “production ready” declaration.

⸻

7. Production Transaction Readiness Checklist

Create a concise internal verification checklist covering the complete payment lifecycle:

User initiates payment
→ Evenum creates/initiates the transaction
→ FlowPay processes the transaction
→ payment status changes
→ Evenum receives/obtains the resulting status
→ Evenum updates the relevant business record
→ user receives the correct result
→ transaction can be reconciled.

Run this against every implemented monetary context in Evenum, including applicable:

* ticket purchases
* event registrations
* campaign collections
* contributions
* paid voting flows
* other implemented collection flows.

Do not assume that every payment context behaves identically. Inspect each actual implementation.
